# CloudCC 全局对象字段模型设计指南

## Agent 工作流

1. 读取平台能力：

```bash
cloudcc doc platform/dataModeling introduction
cloudcc doc platform/dataModeling devguide
cloudcc doc platform/standardCapabilities introduction
cloudcc doc platform/standardCapabilities devguide
cloudcc doc platform/object introduction
cloudcc doc platform/object devguide
cloudcc doc platform/fields introduction
cloudcc doc platform/fields devguide
cloudcc doc platform/globalSelectList introduction
cloudcc doc platform/globalSelectList devguide
cloudcc doc platform/recordType devguide
cloudcc doc platform/pagelayout devguide
```

2. 读取目标租户标准能力目录。任何对象字段建模前，都必须先执行只读扫描，输出目标租户已经启用的标准应用、菜单、标准对象、标准字段和自定义扩展：

```bash
cloudcc scan msapi <projectPath> standard-catalog
```

扫描结果必须作为 `01-standard-environment-baseline.md` 的证据来源。标准目录至少要检查：

- CRM 全流程标准对象，例如客户、联系人、线索、商机、市场活动、订单、合同、产品、价格、发票、回款、服务工单、活动、任务、客户小组等。
- 标准云应用承载能力，例如商务云、CPQ、现场服务云、客户服务云、项目云、伙伴云、利润云，以及客户租户中实际安装的其他标准应用。
- 标准对象字段属性，例如字段 API、字段标签、字段类型、是否标准/自定义、必填、唯一、引用对象、全局选项列表引用。
- 标准应用菜单、对象菜单、页面布局、记录类型、视图、角色、简档和共享规则。

未扫描到的标准能力只能标注为“待确认”，不能在方案中假定存在；已扫描到的标准对象和字段必须优先进入复用评估。

3. 先建立全局模型，再进入模块设计：

```text
标准环境基线
  -> 全局对象地图
  -> 对象关系矩阵
  -> 全局对象字段字典
  -> 状态机矩阵
  -> 全局选项列表清单
  -> 权限和页面影响
  -> 模块设计
```

4. 输出任何对象字段方案前，必须先说明：

```text
标准能力扫描证据：
标准应用/标准对象是否已存在：
是否复用标准对象：
是否需要自定义对象：
是否已有同义字段：
是否已有全局选项列表：
是否影响权限/页面/报表/接口：
```

对象设计默认顺序：

```text
复用标准对象和标准字段
  -> 扩展标准对象字段/记录类型/布局
  -> 复用标准关联对象或标准团队/共享能力
  -> 使用自定义对象承载标准能力无法表达的业务实体
```

## 标准产出物与文档命名规范

CloudCC 项目必须把全局建模产出物沉淀成固定文件。文件名使用小写英文短语和连字符，文档标题可以使用中文。这样既方便客户阅读，也方便 Git、脚本、MSAPI plan 和上线证据引用。

### 目录结构

客户项目交付文档建议统一放在：

```text
docs/delivery/<project-code>/
├── 00-governance/
├── 01-blueprint/
├── 02-global-modeling/
├── 03-module-design/
├── 04-security/
├── 05-integration/
├── 06-data-migration/
├── 07-testing-cutover/
└── 08-release-evidence/
```

命名规则：

- `<project-code>` 使用客户或项目英文短码，例如 `sunpaper-crm`、`dealer-crm`。
- 目录编号固定两位数字，用于表达阅读和实施顺序。
- 文件名固定使用 `<NN>-<artifact-key>.md`。
- 大表可增加同名 `.xlsx` 附件，但 `.md` 文件仍作为说明、口径、责任人和评审状态入口。
- 不在文件名中使用空格、中文、随机编号或个人姓名。

### 版本与快照命名

稳定工作文件保持固定文件名，不在主文件名里追加日期或版本号。需要对外评审、签字、归档或上线留证时，在当前目录下创建 `snapshots/`：

```text
docs/delivery/<project-code>/02-global-modeling/snapshots/
```

快照文件名使用：

```text
<YYYYMMDD>-<artifact-key>-v<major>.<minor>-<status>.<ext>
```

示例：

```text
20260617-global-object-field-dictionary-v1.0-review.md
20260617-global-object-field-dictionary-v1.0-approved.xlsx
20260617-global-select-list-catalog-v1.0-approved.pdf
```

状态建议：

```text
draft：顾问内部草稿
review：客户或项目组评审中
approved：已确认，可作为实施输入
superseded：已被新版本替代
archived：历史归档
```

版本规则：

- `v0.x`：内部草稿，不能作为真实系统写入依据。
- `v1.0`：首个客户或项目负责人确认版本。
- `v1.1`：不改变对象或字段语义的小修订。
- `v2.0`：对象边界、字段语义、状态机或权限影响发生实质变化。

## 标准环境基线检查

使用标准初始化的 CloudCC 环境作为基线时，建议先检查：

- 标准应用清单，包括 CRM、商务云、CPQ、现场服务云、客户服务云、项目云、伙伴云、利润云等目标租户实际启用的应用。
- 标准菜单清单和菜单关联对象。
- 标准对象清单，区分标准对象和自定义对象。
- 标准字段清单，区分标准字段和自定义字段。
- 标准页面布局。
- 标准记录类型。
- 标准全局选项列表。
- 标准角色、简档和权限结构。
- 标准应用、菜单和视图。

不要在未确认标准能力前直接创建自定义对象和字段。

### 标准能力目录快照

建议把 `standard-catalog` 的脱敏结果保存到：

```text
docs/delivery/<project-code>/02-global-modeling/snapshots/<YYYYMMDD>-standard-capability-catalog-v0.1-draft.json
```

`01-standard-environment-baseline.md` 必须从该快照提炼：

| 能力域 | 标准应用 | 标准对象 | 标准字段/关系 | 复用结论 | 扩展点 | 自定义缺口 |
|---|---|---|---|---|---|---|

示例判断：

| 业务概念 | 优先检查标准能力 | 自定义对象准入条件 |
|---|---|---|
| 客户多人协同 | 客户小组/客户团队、共享规则、角色层级 | 标准客户小组无法表达业务线、区域、目标或生命周期口径 |
| 报价/价格 | CPQ、价格本、产品、报价、订单 | 标准 CPQ 未启用或生命周期与审批语义不匹配 |
| 现场服务 | 现场服务云、工单、派工、服务资源、服务报告 | 标准工单无法承载客户定制闭环 |
| 客户门户 | 伙伴云、外部用户、门户应用和共享规则 | 标准伙伴云许可或对象共享无法满足业务 |
| 利润分析 | 利润云、预算、成本、利润分析对象 | 标准利润云未启用或分析口径需单独快照 |


关系类型建议：

- 子记录权限是否由父对象继承。
- 是否需要累计汇总。

## 全局对象字段字典模板

全局对象字段字典是创建和调整真实 CloudCC 对象字段的准入清单。没有进入全局对象字段字典的字段，不应直接在真实系统中创建。

全局对象字段字典不直接维护完整全局选项列表值集；选项字段必须声明值集来源，并通过全局选项列表 API 名引用全局选项列表清单。

字段字典不是简单的字段名翻译表，而是元数据处置决策表。每一行必须先判断是否真的要成为 CloudCC 对象字段，再决定目标字段 API。

```text
| 对象标签 | 字段标签 | API 名 | 字段类型 | 字段处置 | API 来源 | 证据来源 | 待确认原因 | 必填 | 唯一 | 默认值 | 来源 | 维护方式 | 是否选项字段 | 选项来源 | 全局选项列表 API | 本地选项值 | 是否报表 | 是否集成 | 权限等级 | 页面位置 | 说明 |
|---|---|---|---|---|---|---|---|---|---|---|---|---|---|---|---|---|---|---|---|---|---|
```

字段处置必须使用受控值：

```text
创建字段：需要在 CloudCC 目标对象上创建新字段
复用标准字段：目标租户标准字段已能承载该含义
复用现有自定义字段：目标租户已有自定义字段可复用
不建字段：业务或系统不需要在 CloudCC 元数据中承载
迁移定位键：仅用于历史数据定位、去重或关联导入批次
源编码映射：仅用于源系统编码和值映射，不直接建字段
仅crosswalk：只进入迁移 crosswalk 或映射表
系统字段：由 CloudCC 平台已有系统字段承载
全局选项集：本行描述的是共享值集或选项值，不是对象字段
待确认：确实缺少目标租户、业务冻结或人工确认依据
```

API 来源必须使用受控值：

```text
最终设计明确：最终设计、字段说明或映射表文本中已经写明 API
结构化列明确：汇总表 targetFieldApi 等结构化列已经给出 API
英文源字段规范化：源字段为清晰英文业务名，按 snake_case 规范化
中文拼音生成：无明确英文/API 设计时，按中文命名规则兜底生成
标准字段扫描匹配：由 standard-catalog 或字段扫描确认可复用标准字段
现有字段扫描匹配：由目标租户扫描确认可复用现有自定义字段
人工确认：经业务/平台负责人确认
不适用：不创建或不承载为对象字段
```

严禁把 `待定` 作为泛化兜底值。若历史材料中出现 `待定`，必须重分类为上述字段处置之一；只有确实缺少证据且需要人工确认的行才保留 `待确认`，并填写待确认原因。

选项来源建议：

```text
none：非选项字段
local：当前对象当前字段独立维护的普通选项列表
global：引用全局选项列表清单中的共享值集
```

字段来源建议：

```text
user：用户录入
system：系统生成
formula：公式计算
trigger：触发器回写
integration：外部系统同步
import：数据导入
sidecar：外挂服务写入
```

维护方式建议：

```text
manual：人工维护
auto：系统自动维护
readonly：只读展示
external：外部系统主维护
mixed：内外部共同维护，需明确主责
```

权限等级建议：

```text
public：普通字段
internal：内部字段
sensitive：敏感字段
secret：密钥或高敏字段，不应进入普通页面和报表
```

## 字段 API 决策顺序

字段 API 不是“中文字段名转拼音”的单一路径结果。生成或修订字段字典时，按以下顺序决策：

1. 最终设计、字段说明、映射规则或评审纪要中已经出现明确 API 时，直接采用。例如 `highest_review_revenue`、`crf_no`、`source_non_sme_id`、`deposit_amount`、`ec_start_date`。不要再按中文标签重新生成拼音 API。
2. 结构化列中已有明确 `targetFieldApi`、`apiName` 或等价字段，且不是空值、`待定`、非法字符或明显占位值时，采用该值。
3. 源字段是清晰英文业务字段且项目允许英文 API 时，按 snake_case 规范化。例如 `Deposit Amount` 生成 `deposit_amount`，`CRF No` 生成 `crf_no`，`SME ID` 生成 `sme_id`。常见缩写使用小写片段保留语义，如 `id`、`crf`、`sme`、`ec`。
4. 字段标签为中文且无明确英文/API 规范时，才按中文拼音规则兜底生成。
5. 仍无法确认时，标记字段处置为 `待确认`，填写待确认原因，并禁止进入 MSAPI plan。

英文源字段不能自动等同于创建字段。`Status_ID`、`Company ID`、`Legacy_ID`、`Source_Record_ID` 等字段必须先判断用途：若仅用于迁移定位、源编码映射或 crosswalk，应分别标记为 `迁移定位键`、`源编码映射` 或 `仅crosswalk`；只有业务要求在 CloudCC 长期保留、展示、查询、集成或报表使用时，才进入 `创建字段` 或 `复用字段`。

## MSAPI plan 前置门禁

从全局对象字段字典生成 MSAPI plan 前必须执行门禁：

- `字段处置=创建字段`：必须有合法 API 名、字段类型、目标对象和证据来源。
- `字段处置=复用标准字段` 或 `复用现有自定义字段`：必须有扫描证据或人工确认记录。
- `字段处置=不建字段`、`迁移定位键`、`源编码映射`、`仅crosswalk`、`系统字段`、`全局选项集`：禁止生成 `fields create/update`。
- `字段处置=待确认`：禁止进入 plan，必须先补齐确认依据。
- `API 名=待定`、空值、明显占位值或非法字符：一律视为阻断错误，不允许生成 MSAPI plan。

全局选项集和值集行必须进入 `06-global-select-list-catalog.md`；字段字典只保留选项字段引用关系，例如 `选项来源=global` 和 `全局选项列表 API`。

## 默认中文标签和 API 命名规范

### 总原则

- 标签默认用中文。
- API 名优先按“字段 API 决策顺序”确定；中文拼音只作为没有明确英文/API 设计时的兜底规则。
- 适用于对象、字段、全局选项列表、记录类型、页面组件等所有需要命名的元数据，不只适用于某一种功能。
- 两个字用全拼。
- 三个字及以上用单字拼音首字母。
- API 名尽量短，不加无关后缀。
- 同一业务含义在不同对象中尽量使用同一 API 片段。
- 如平台要求唯一且发生冲突，先加业务域限定词，而不是加无意义长后缀。

### 示例

| 类型 | 标签 | 推荐 API | 说明 |
|---|---|---|---|
| 对象 | 客户 | `kehu` | 两个字，全拼 |
| 对象 | 服务工单 | `fwgd` | 四个字，首字母 |
| 字段 | 目标金额 | `mbje` | 四个字，首字母 |
| 字段 | 合同编号 | `htbh` | 四个字，首字母 |
| 字段 | 同步状态 | `tbzt` | 四个字，首字母 |
| 字段 | 外部编号 | `wbbh` | 四个字，首字母 |
| 字段 | 是否有效 | `sfyx` | 四个字，首字母 |
| 字段 | 客户等级 | `khdj` | 四个字，首字母 |
| 字段 | 省 | `sheng` | 一个字，全拼 |
| 字段 | 城市 | `chengshi` | 两个字，全拼 |

### 不推荐

```text
mbje_custom_c_field
target_amount_custom_field
fwgd_custom_object
sync_status_custom_c
kh_obj
```

### 冲突处理

如果同一对象内 API 名冲突，按以下顺序处理：

1. 检查是否是重复字段，应合并而不是新建。
2. 增加必要业务域前缀，如 `xsje` 销售金额、`fwje` 服务金额。
3. 增加必要维度前缀，如 `mbje` 目标金额、`sjje` 实际金额。
4. 不使用 `_custom`、`_field`、`_c` 等无业务意义后缀。

## 全局选项列表清单治理

本节是建模方法论。全局选项列表清单是跨对象值集治理清单；全局选项列表的功能事实、后台入口、字段依赖性、已删除值集、CLI 创建/查询/详情/删除能力，以 `platform/globalSelectList introduction` 和 `platform/globalSelectList devguide` 为准。

平台事实摘录：

- 全局选项列表是跨对象共享的值集机制。
- 多个对象的选项列表字段可复用同一套值集。
- 修改全局选项列表后，所有引用字段同步更新。
- 字段依赖性可用于查看引用该值集的对象字段。
- 省州、县区、国家、市是典型内置全局选项列表。

### 适合全局选项列表

通用、跨对象复用、需要统一维护或接口映射的选项，适合做成全局选项列表：

- 国家、省、市、地区。
- 行业、客户类型、证件类型。
- 通用等级、优先级、风险等级、重要程度。
- 跨对象复用的业务类型、状态、阶段。
- 外部系统需要编码映射的选项。
- 平台级全局属性和通用状态。

### 不适合全局选项列表

- 只在单个对象使用的临时选项。
- 应该建为主数据对象的数据，如产品、服务网点、员工、工程师。
- 高频新增、停用、合并且需要权限和历史的业务数据。
- 依赖父记录动态过滤的数据。

### 全局选项列表清单模板

```text
| 列表标签 | API 名 | 适用对象 | 选项值 | 排序方式 | 默认值策略 | 是否有编码 | 是否接口映射 | 维护人 | 是否允许停用 | 说明 |
|---|---|---|---|---|---|---|---|---|---|---|
```

### 选项值治理

- 不建议删除已被历史数据使用的选项值，优先停用。
- 需要接口映射时，为选项维护外部编码。
- 状态类选项变更必须评估流程、报表和自动化影响。
- 国家、省、市等通用属性优先全局化，避免每个对象重复维护。

### 字段引用实现

创建或调整字段时，先读取 `platform/fields devguide`：

- 选项列表字段如需引用全局选项列表，需要设置 `useGlobalSelect`。
- `useGlobalSelect` 为启用时，需要传入 `globalSelectId`。
- `globalSelectId` 应来自 `cloudcc get globalSelectList` 或 `cloudcc detail globalSelectList` 的结果。
- 字段方案输出时，必须写明“普通选项列表”还是“全局选项列表引用”。
- 全局选项列表自身的 API 名也遵循全局命名规范，例如 `客户等级` 推荐 `khdj`，不要默认写成 `customer_level` 或超长后缀名。客户项目已有明确英文 API 规范时，以项目规范为准。

## 报表口径字段

报表需要稳定字段，不应完全依赖临时公式或前端计算。

常见报表字段：

- 金额类：目标金额、预计金额、实际金额、含税金额、未税金额。
- 时间类：创建时间、提交时间、审批通过时间、完成时间、关闭时间。
- 归属类：负责人、所属部门、区域、渠道、服务网点。
- 状态类：业务状态、审批状态、同步状态、结算状态。
- 周期类：年度、季度、月份、账期。

## 建模评审清单

- 是否先检查了标准对象和标准字段？
- 是否存在重复对象？
- 是否存在同义字段？
- 真实对象字段是否全部先进入全局对象字段字典？
- 全局建模产出物是否使用固定目录和固定文件名？
- 是否区分稳定工作文件和评审/归档快照？
- 文档头信息是否包含状态、版本、负责人、上游依据和下游影响？
- 标签是否使用中文？
- API 名是否符合拼音规则？
- 是否避免了无意义长后缀？
- 主数据、过程、交易、明细、日志、配置对象是否分层清楚？
- 查找和主详关系是否符合生命周期？
- 状态字段是否拆分为业务、审批、同步等不同维度？
- 全局选项列表是否只承载通用可复用属性？
- 选项字段是否明确普通选项或全局选项列表引用？
- 需要独立权限、历史和生命周期的数据是否建成对象而不是选项？
- 集成字段是否有幂等键、状态、错误和时间？
- 报表口径字段是否稳定？
- 页面布局和移动端录入是否已考虑？
- 数据导入和历史迁移是否已考虑？
