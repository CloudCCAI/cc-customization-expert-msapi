# CloudCC 蓝图输出指南

## Agent 工作流

1. 读取平台能力：

```bash
cloudcc doc platform/overview introduction
cloudcc doc platform/capabilityMap introduction
cloudcc doc platform/lowcodeHighcode devguide
```

2. 判断项目类型：

```text
销售管理 / 渠道管理 / 售后服务 / 资产服务 / 小程序门户 / 集成中台 / 复合型营销服一体化
```

3. 建立蓝图骨架：

```text
业务范围 -> 流程框架 -> 功能模块 -> 对象模型 -> 权限模型 -> 自动化和代码扩展 -> 集成设计 -> 阶段计划
```

4. 对每个模块使用模块卡片：

```bash
cloudcc doc methodology/moduleDesign devguide
```

5. 对每个接口使用接口卡片：

```bash
cloudcc doc methodology/integrationDesign devguide
cloudcc doc platform/integrationPatterns devguide
```

## 章节质量检查

### 项目概述

应包含：

- 业务背景和痛点
- 当前系统边界
- 本期建设范围
- 不在本期范围的内容
- 建设目标和衡量口径

避免：

- 只写口号，没有范围。
- 未说明哪些能力依赖外部系统。
- 把未来阶段当成本期承诺。

### 业务流程

应包含：

- 端到端流程框架，如 MPR、MTL、LTC、ITR。
- 角色和职责。
- 状态变化。
- 自动生成、人工创建、审批、回写、关闭等关键节点。

避免：

- 只有页面功能，没有业务闭环。
- 没有异常分支。
- 没有定义谁能发起、谁能审批、谁能关闭。

#### 流程图治理

- 创建、修改或评审流程图前，先读取 `methodology/projectGovernance devguide`、项目 `AGENTS.md` 和适用的项目标准。
- L0/L1 实际流程图进入 `docs/delivery/<project-code>/01-blueprint/processes/`；L2/L3 进入对应 FEAT、模块详细设计或集成设计。
- 图形、颜色、泳道、节点命名和评审方法属于项目标准；当前业务主链路、角色、系统职责和优先级分别引用蓝图、FEAT、ADR、接口契约和任务板。
- 不存在项目标准时，只使用通用表达建议，不擅自把示例颜色、节点数量或泳道顺序升级为全项目硬规则。
- 每张正式流程图必须登记事实源、状态和评审证据；静态检查或自动化测试不能替代业务责任人确认。

### 功能架构

应包含：

- 模块清单。
- 标准对象和自定义对象的分工。
- 记录类型、相关列表、状态机。
- 页面、按钮、pagecomponent 的边界。
- 报表和看板。

避免：

- 所有需求都写成自定义对象。
- 忽略权限、共享和数据可见性。
- 对象关系没有主从、查找、生命周期说明。

### 系统集成

应包含：

- 对接系统。
- 数据流向。
- 触发时机。
- 调用方式。
- 同步状态。
- 错误处理。
- 是否需要 sidecar。

避免：

- 只写“与 SAP 集成”这种泛化描述。
- 没有幂等键。
- 没有回调和重试策略。
- 未说明实时、定时和人工按钮触发的边界。

## 输出前检查

```text
是否覆盖业务范围？
是否有端到端流程？
是否每个模块都有对象、页面、规则、自动化、接口、报表？
是否区分平台事实和方法论建议？
是否有待确认事项？
是否避免客户私有信息进入通用模板？
```
