# CloudCC 项目蓝图方法论

## 定位

本模块用于指导 AI Agent 输出 CloudCC PaaS 项目的蓝图设计报告。蓝图不是功能清单堆砌，而是把业务流程、对象模型、平台能力、集成边界和实施阶段组织成可评审、可落地、可验收的设计文件。

事实依据：

- CloudCC 平台具备对象、字段、页面布局、权限、角色、触发器、类、定时作业、pagecomponent、OpenAPI、移动端和应用配置能力。
- 当前技能项目约定前端在 `frontend/`，后端 class、trigger、schedule 在 `backend/`，外挂中间程序在 `sidecar/`。
- 已阅读的真实 CloudCC 营销管理平台蓝图文档采用了项目概述、业务流程、功能架构、详细设计、系统集成、实施阶段计划的组织方式。

方法论说明：

- 下文为项目实施方法论抽象，不代表 CloudCC 后台固定菜单或强制模板。
- 不应把客户名称、接口地址、内网环境、项目专有评分阈值、岗位名称原样写入通用方案。

## 蓝图的目标

CloudCC 项目蓝图应回答六个问题：

1. 为什么建设：业务背景、范围和目标。
2. 业务怎么跑：端到端流程、角色、状态、关键控制点。
3. 平台怎么承载：对象、字段、页面、权限、自动化、代码扩展。
4. 系统怎么集成：对接系统、数据流向、触发时机、同步状态、异常处理。
5. 如何分阶段上线：里程碑、依赖、验收范围。
6. 哪些还未确认：待确认规则、接口、数据量、权限边界和运维责任。

## 推荐章节

```text
1. 项目概述
   1.1 项目背景
   1.2 业务范围
   1.3 系统建设目标
   1.4 设计原则

2. 业务流程设计
   2.1 核心流程框架
   2.2 L1-L4 流程分解
   2.3 角色与职责
   2.4 流程控制点

3. 功能架构设计
   3.1 整体功能架构
   3.2 模块设计
   3.3 对象关系
   3.4 权限与数据可见性

4. 详细实现设计
   4.1 对象、字段、记录类型
   4.2 页面、按钮、pagecomponent
   4.3 验证规则、审批、触发器、类、定时作业
   4.4 报表和看板

5. 系统集成设计
   5.1 集成全景
   5.2 接口清单
   5.3 实时、定时、回调和 sidecar 边界
   5.4 同步状态、异常、重试和监控

6. 实施阶段计划
   6.1 阶段范围
   6.2 里程碑
   6.3 依赖与风险
   6.4 验收口径

7. 待确认事项
```

## 设计原则

- 端到端优先：先确认业务闭环，再拆对象和页面。
- 平台优先：能用配置、权限、流程、自动化解决的，不急于写代码。
- 高代码有边界：触发器、类、pagecomponent、sidecar 分别承担不同职责。
- 集成可观测：同步状态、请求号、外部编号、错误摘要和重试入口应在设计阶段定义。
- 分阶段落地：营销、销售、服务、集成可以有先后，但对象和主数据边界要提前规划。
- 待确认显式化：未确认项必须列出，不要用假设填平。
