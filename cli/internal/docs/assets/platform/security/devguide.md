# CloudCC 权限设计指南

## 设计顺序

### 1. 先定义用户群体

识别业务角色、组织层级、是否存在外部用户或集成用户。

相关能力：

- user
- role
- profile
- permission

### 2. 再定义对象操作权限

按对象决定：

- 只读
- 新建
- 编辑
- 删除
- 查看全部
- 修改全部

原则：先给最小权限，再通过权限集补充特殊能力。

### 3. 再定义记录可见性

需要确认对象默认共享策略，以及是否通过角色层级或共享规则扩展。

需要用户确认：

- 是否同级互不可见
- 上级是否能看下级
- 是否按区域、公用小组、队列共享
- 是否按记录字段条件共享

角色和共享规则应作为数据权限主线实施：`role` 定义组织层级和上下级可见性，`sharingRule` 定义角色层级之外的共享例外。

### 4. 再定义字段级安全

敏感字段先通过字段级安全控制可见和只读，不要只依赖页面布局隐藏。

手册明确区分字段可见和只读：

- 可见：用户简档可看到该字段。
- 只读：用户不可编辑该字段。

### 5. 再定义登录与身份策略

如涉及企业统一身份，查看 IdP/SSO 文档。

```bash
cloudcc doc platform/identityProvider devguide
cloudcc doc platform/singleSignOn devguide
```

## 推荐实践

以下为行业通用权限设计经验，需结合客户组织确认：

- 简档用于基础岗位权限，不要为每个用户创建一个简档。
- 权限集用于临时或跨岗位补充权限。
- 字段级安全用于敏感字段，不要只用页面隐藏。
- 共享规则只扩展访问，不应当替代组织角色模型。
- 上线前必须用目标用户账号做应用、菜单、对象、字段、记录五层验收。

## MSAPI 实施域

除高代码外，权限相关低代码元数据应进入 MSAPI：

```bash
cloudcc plan msapi roles @role.json
cloudcc plan msapi profiles @profile.json
cloudcc plan msapi permissions @permission.json
cloudcc plan msapi sharing-rules @sharing-rule.json
```

写入后保留 `planId`、`operationId`，并使用 `changes`、`rollback-plan`、`rollback` 形成可审计证据。

## 验收清单

- 目标用户能否登录？
- 是否只看到应看到的应用？
- 是否只看到应看到的菜单？
- 对象新建/编辑/删除权限是否符合岗位？
- 敏感字段是否不可见或只读？
- 私有记录是否不会越权可见？
- 共享规则是否只扩大到目标人群？
- 移动端是否继承了预期权限？
- 集成用户是否使用单独账号和最小权限？

## 待确认点

当前技能文档没有完整覆盖所有后台安全页面的 CLI 操作。涉及密码策略、登录时间、登录 IP、审计日志等配置时，应以后台页面和实际租户能力为准。
