# CloudCC 能力路由指南

## 路由步骤

### 1. 判断需求类型

| 用户表达 | 优先归类 |
|---|---|
| “新增一个业务模块/台账/表单” | 数据建模 + 应用入口 |
| “查询/新增/修改/删除业务记录” | OpenAPI 常规业务数据 CRUD |
| “大批量导入/初始化数据” | dataBulk 离线批处理 |
| “创建/优化数据库索引” | dataIndex 索引优化 |
| “字段要联动/必填/不能重复” | 数据质量 |
| “不同角色看到不同数据” | 权限治理 |
| “审批/通知/自动更新” | 自动化 |
| “页面标准能力不够” | 前端扩展 |
| “和外部系统打通” | 集成 |
| “手机端使用” | 移动端 |
| “从测试迁到生产” | ALM 交付 |

### 2. 优先选择低代码能力

除非用户明确要求代码或低代码无法满足，否则优先使用：

- 对象/字段
- 页面布局
- 菜单/应用
- 验证规则
- 查重过滤器
- 工作流/批准
- 权限和共享配置

### 3. 再升级到高代码

以下情况再考虑高代码：

- 需要复杂算法或跨多对象事务逻辑
- 需要外部接口调用和失败补偿
- 需要复杂 UI 或复杂前端交互
- 需要周期性后台处理
- 需要标准配置无法表达的保存前/保存后逻辑

外部接口调用还要继续区分方向：外部系统调用 CloudCC 使用 OpenAPI；CloudCC 自定义类、触发器调用的类或定时类主动调用外部 HTTP 服务，使用 `apiRegistrar -> CCRemoteClient`。后者先完成注册、服务端调试和 `ACTIVE` 状态确认，再生成只引用 `apiCode` 的高代码。

业务数据操作还要区分日常 CRUD 与批量导入：标准 CRM 对象和自定义对象的日常查询、新增、修改、删除和 upsert 统一使用 OpenAPI；dataBulk 仅用于大批量数据导入、初始化和离线批处理，不用于日常业务场景。

## 常见错误

- 只因为能写触发器，就把所有逻辑写入触发器。
- 只因为能做自定义组件，就忽略页面布局和客户端脚本。
- 只讨论对象字段，不讨论简档、共享和移动端布局。
- 只考虑创建功能，不考虑数据导入、迁移、回滚和权限验收。
- 在没有事实依据时编造后台接口。
