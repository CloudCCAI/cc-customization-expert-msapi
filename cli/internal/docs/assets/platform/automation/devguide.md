# CloudCC 自动化设计指南

## 设计步骤

### 1. 明确触发时机

先回答：

- 是保存前必须阻止？
- 是保存后自动补充？
- 是需要人工审批？
- 是按时间批量执行？
- 是外部系统回调或同步？

### 2. 明确执行主体

- 配置规则：验证规则、查重、工作流、批准
- 服务端代码：触发器、类、定时类
- 外部能力：Webhook、OpenAPI、sidecar

### 3. 明确失败处理

需要区分：

- 阻塞式失败：保存失败并提示用户
- 非阻塞式失败：记录日志、重试、人工处理
- 审批失败：拒绝、退回、调回
- 定时失败：下次重试或补偿

## 低代码优先

优先使用：

- 字段类型和必填控制
- 验证规则
- 查重过滤器
- 工作流和批准
- 字段更新、任务、邮件、短信动作

当这些能力无法表达复杂逻辑时，再升级到触发器、类、定时类或 sidecar。

## 高代码使用边界

适合触发器：

- 需要跨对象查询和更新
- 需要保存事件中的复杂判断
- 需要保证业务逻辑强执行

适合类：

- 多处复用的服务端逻辑
- 自定义页面或组件需要调用的后端能力
- 复杂集成前的业务封装

适合定时类：

- 周期性提醒
- 数据修正和回填
- 批量同步
- 失败补偿
- 报表底表刷新

## 行业通用注意事项

以下为通用工程经验，具体执行顺序和限制需结合实际租户验证：

- 不要把所有逻辑堆进一个触发器。
- 避免触发器递归更新同一对象。
- 触发器内避免大量逐条查询和逐条更新。
- 外部接口调用要考虑超时、重试、幂等和日志。
- 定时任务要有执行窗口、失败处理和数据范围控制。
- 审批流变更前要确认历史在途审批如何处理。

## Agent 方案输出清单

- 触发时机
- 使用的自动化能力
- 是否阻塞保存
- 是否需要人工审批
- 是否需要代码
- 是否需要定时任务
- 是否需要外部系统
- 失败处理方式
- 验收路径
