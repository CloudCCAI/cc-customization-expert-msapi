# CloudCC 字段介绍

## 1. 什么是字段

字段是对象上的数据属性定义，用于描述一条记录中每个信息项的结构与含义。

你可以把字段理解为：

- 业务数据的最小单元
- 对象模型的具体列定义
- 页面录入、查询、统计和自动化逻辑的基础

从 CloudCC
平台的角度看，字段就是对象的属性。姓名、手机、金额、状态、日期、负责人、附件等信息，本质上都是通过字段来承载的。

---

## 2. 标准字段与自定义字段

CloudCC 对象上的字段通常分为两类：

- 标准字段：平台预置字段，属于对象默认能力的一部分
- 自定义字段：企业根据自身业务场景新增、维护和删除的字段

所有对象通常都带有一些共通标准字段，例如：

- 对象记录名
- 创建时间
- 创建人
- 最后修改时间
- 最后修改人
- 所有人

当标准字段无法表达业务信息时，就需要通过自定义字段去补充业务含义。

---

## 3. 字段模块能做什么

`fields` 模块用于围绕对象管理字段，当前支持：

- 查询对象字段（标准字段 + 自定义字段）
- 查询字段详情
- 创建字段
- 更新字段（需字段 ID）
- 删除字段

可通过以下命令读取文档：

```bash
cloudcc doc platform/fields introduction
cloudcc doc platform/fields devguide
```

---

## 4. 字段在系统中的作用

字段决定了对象能记录什么信息、如何被录入、如何被展示以及如何参与流程。

常见作用包括：

- 定义业务属性（如名称、金额、状态、日期）
- 驱动页面展示和表单校验
- 支撑筛选、排序、报表统计
- 作为触发器和后端逻辑的判断条件
- 为自动化、审批、报表和搜索提供数据基础

如果对象是业务模型的骨架，那么字段就是业务模型的具体内容。

---

## 5. 为什么要重视字段设计

字段设计质量会直接影响：

- 数据录入是否清晰
- 报表口径是否统一
- 查询筛选是否高效
- 流程和代码是否容易维护

字段设计不合理时，常见问题包括：

- 同类信息分散在多个字段里
- 命名混乱，后续脚本和接口难维护
- 页面录入项过多或缺失，影响使用体验
- 统计分析无法统一口径
- 自动化逻辑和触发器条件复杂、难排查

因此，字段管理不是简单“加几个列”，而是业务建模和数据治理的重要部分。

---

## 6. 什么时候需要管理字段

通常在以下场景需要使用 `fields` 模块：

- 新建对象后，需要补齐业务字段
- 业务流程变化，需要新增或调整字段结构
- 数据治理中，需要清理不再使用的字段
- 接口联动或自动化逻辑需要新增数据位
- 页面、报表、审批、搜索需要新增业务属性

---

## 7. 常见业务场景

字段设计常见于以下业务场景：

- 销售场景：金额、预计签约日期、成交概率、阶段
- 服务场景：工单状态、处理时间、满意度评分、附件图片
- 项目场景：项目阶段、负责人、里程碑时间、进度说明
- 资产场景：设备编号、安装地址、巡检周期、归属客户
- 渠道场景：渠道级别、返佣比例、合作到期日、联系人信息

很多企业在标准 CRM
之外扩展业务时，真正落地管理的第一步往往不是写代码，而是先把字段设计清楚。

---

## 8. 平台能力与 CLI 能力的关系

根据 CloudCC
官方文档，平台层面支持丰富的字段体系，包括文本、URL、百分比、币种、数字、文本区、长文本、富文本、电话、电子邮件、日期、日期/时间、评分、选项列表、图片、查找关系、主详信息关系、公式、自动编号、累计汇总、查找多选、复选框等类型。

当前 `cloudcc-cli` 的 `fields`
模块通过 MetadataService spec 覆盖平台开放字段编码，用于自动化创建和管理字段。旧版位置参数快捷命令仍可用于部分基础字段，但不作为完整字段能力的说明来源。

字段元数据中的 `dataFieldRef` 不是业务 API 名，而是当前对象底层数据表中的物理存储槽位（例如 `str_field1`）。同一对象内，一个非 `none` 的物理槽位只能属于一个字段。通过 MetadataService 创建字段时，服务会读取 `tp_sys_schemetable` 的现有映射，并按字段类型分配首个可用空槽；调用方通常不应自行复制或硬编码该值。

因此在实际使用时，需要区分两种 CLI 入口：

- MetadataService spec：推荐入口，覆盖基础字段、关系字段、公式、自动编号、累计汇总、地址、地理定位、权限、布局落位等完整元数据配置。
- 位置参数快捷命令：兼容入口，只适合少量基础字段模板，不适合表达高级字段元数据。

命令开发与自动化脚本，应优先参考 `cloudcc doc platform/fields devguide` 中的 MetadataService spec 示例和参数说明。

## 9. 字段列表说明

从业务理解角度，可以把常见字段类型分成下面几组：

### 9.1 基础信息字段

1. 文本（`S`）：用于姓名、编号、标题、简称等
2. 数字（`N`）：用于数量、次数、评分基数等
3. 币种（`c`）：用于金额、预算、合同额、回款额等
4. 百分比（`P`）：用于概率、折扣率、完成率等
5. 复选框（`B`）：用于是/否类状态

### 9.2 时间类字段

1. 日期（`D`）：用于开始日期、截止日期、签约日期等
2. 时间（`T`）：用于预约时间、提醒时间等
3. 日期/时间（`F`）：用于更精确的业务时间点，如处理时间、提交时间、完成时间

### 9.3 联系方式与标识类字段

1. 电话（`H`）：用于手机、座机、联系方式
2. 电子邮件（`E`）：用于邮箱地址
3. URL（`U`）：用于官网、资料链接、外部系统地址

### 9.4 文本内容类字段

1. 文本区（`X`）：用于备注、补充说明、简短描述
2. 文本区（长）（`J`）：用于较长说明、详细记录、过程描述
3. 文本区（富文本）（`A`）：用于图文混排的业务说明、通知内容、知识内容

### 9.5 选择类字段

1. 选项列表（`L`）：用于状态、阶段、分类、来源、优先级等单选场景
2. 选项列表（多选）（`Q`）：用于标签、能力项、覆盖区域、产品范围等多选场景

### 9.6 关系类字段

1. 查找关系（`Y`）：用于把一条记录关联到另一对象
2. 主详信息关系（`M`）：用于建立主从结构，适合主表与明细表场景
3. 查找多选（`MR`）：用于一条记录关联多个对象值

这类字段通常用于：

1. 客户和联系人
2. 项目和客户
3. 合同和回款计划
4. 主记录和明细记录

### 9.7 媒体与附件类字段

1. 图片（`IMG`）：用于头像、产品图、现场照片、凭证图片
2. 文件（`FL`）：用于合同附件、方案文档、交付资料

### 9.8 安全与特殊字段

1. 加密文本（存储加密）（`ENC`）
2. 加密文本（显示加密）（`ENCD`）
3. 评分（`SCORE`）
4. 地址（`AD`）
5. 地理定位（`LT`）

平台层面还支持但通常更偏高级配置的字段类型包括：

1. 公式（`Z`）：创建时准备 `formulaText` 和公式返回类型 `formulaType`；`formulaText` 使用字段 API 名，内部执行表达式由 MetadataService 生成。普通公式字段语法以目标环境字段公式校验结果为准；可用运算符、完整函数清单和 `HYPERLINK(...)`、`IMAGE(...)`、`DOMAIN` 等表达式说明见 `platform/fields devguide`。
2. 自动编号
3. 累计汇总（`C`）

这些字段更适合在有明确建模规则和业务约束时使用。

---

## 10. 与其他模块的关系

字段通常和这些模块联动：

- `object`：字段附着于对象，是对象建模的细化
- `menu` / `application`：字段会影响列表和详情页呈现
- `triggers` / `classes`：字段值常用于业务逻辑判断
- `script` / `plugin` / `customPage`：前端交互通常围绕字段展开

字段设计合理与否，直接影响后续开发效率和数据质量。
